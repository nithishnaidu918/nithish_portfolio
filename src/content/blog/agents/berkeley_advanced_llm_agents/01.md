# Inference-Time Techniques for LLM Reasoning

## 1. Introduction

Large Language Models (LLMs) can answer questions, write code, summarize information, and solve many problems. However, they can still make mistakes, especially on complex mathematical, coding, and reasoning tasks.

One way to improve their performance is to give them more computation while they are solving a problem.

This is called **inference-time scaling**.

Instead of immediately accepting the first answer, we can ask the model to reason more carefully, generate multiple solutions, search through possible approaches, or revise an answer using feedback.

These techniques do not necessarily require retraining the model. They change how the model is used when generating an answer.

The lecture organizes inference-time techniques into three main approaches:

1. **Depth:** Spend more tokens reasoning through one solution.
2. **Width:** Generate multiple candidate solutions and select a promising one.
3. **Iteration:** Repeatedly improve a solution using feedback.

## 2. What is inference time?

Inference is the process of using a trained model to produce an output from an input.

For example:

- Input: A mathematical problem.
- Model: An LLM.
- Output: A solution to the problem.

**Inference-time techniques** change the process used to obtain that output. They may use longer reasoning, multiple model calls, candidate selection, or feedback.

### Inference-time scaling versus training

| Training | Inference-time scaling |
|---|---|
| Changes model parameters through training or fine-tuning. | Uses a model to solve a task at inference time. |
| Requires training data and a training process. | Can often work with an already-trained model. |
| Improvements may generalize across many future tasks. | Additional computation is spent on the current task or task-solving procedure. |

Inference-time scaling is not guaranteed to improve every answer. Its effectiveness depends on the model, task, evaluation method, and available computation.

## 3. Why do reasoning models need more computation?

A standard LLM may generate an answer immediately after receiving a question. A difficult problem, however, may require several intermediate steps.

For example, solving a complicated mathematics problem may involve:

1. Understanding the question.
2. Identifying the relevant information.
3. Breaking the problem into smaller parts.
4. Solving each part.
5. Checking whether the results fit together.
6. Producing the final answer.

Reasoning-oriented models can spend additional computation on such intermediate work. The amount of computation may vary with the difficulty of the problem.

The lecture discusses the progress of reasoning models, including OpenAI's o1 and o3, as motivation for studying these techniques. Its central focus is not a particular model, but the broader question of how to use additional inference-time computation effectively.

# Part 1: Basic Prompting Techniques — Increasing Depth

The first approach is to use more tokens to produce a single, better-developed solution.

## 4. Standard prompting and its limitations

In few-shot prompting, we provide a model with examples of how to answer a task.

For example:

**Example 1**

Question: What is 2 + 3?

Answer: 5.

**Example 2**

Question: What is 4 + 5?

Answer: 9.

These examples show the model the expected question-and-answer format. However, they do not necessarily teach the model how to solve a more complicated problem.

For reasoning tasks, showing only final answers may be insufficient. Examples that demonstrate intermediate reasoning can be more helpful.

## 5. Chain-of-Thought prompting

**Chain-of-Thought (CoT) prompting** encourages the model to generate intermediate reasoning steps before its final answer.

Instead of requesting only the answer, we encourage the model to work through the problem in stages.

For example:

Question: A notebook costs ₹40. How much do five notebooks cost?

A solution can identify the price of one notebook, multiply it by five, and then provide the total.

The important idea is that the model is encouraged to perform intermediate steps rather than jumping directly to a final result.

### Why is CoT useful?

It can help the model:
- Break complex problems into smaller steps.
- Organize calculations.
- Plan a sequence of actions.
- Make intermediate relationships explicit.

The lecture notes that CoT performance can improve significantly as model size increases. Larger models may be better able to benefit from generating intermediate reasoning.

The original scaling experiments discussed in the lecture used pretrained models. Later post-training techniques can change the precise performance trends, so the historical results should not be interpreted as a universal rule for every modern model.

## 6. Zero-shot Chain-of-Thought

Zero-shot CoT asks the model to reason through a problem without providing worked examples.

A simple instruction is:

> Let's think step by step.

This can encourage intermediate reasoning even when no demonstrations are supplied.

The lecture notes that zero-shot CoT can substantially outperform ordinary zero-shot prompting, especially on difficult mathematics and symbolic reasoning tasks.

However, zero-shot CoT can still perform worse than few-shot CoT, where the model receives examples of the desired reasoning pattern.

## 7. Analogical prompting

How can we improve reasoning without manually preparing examples for every problem?

One approach is **analogical prompting**.

The model first recalls or generates examples of related problems, then uses those examples to solve the current problem.

The workflow is:

1. Receive the target problem.
2. Generate relevant examples or previously solved problem patterns.
3. Use the examples to identify a useful approach.
4. Apply the approach to the target problem.
5. Produce the final answer.

### Example

Suppose the model must solve a new problem about calculating the time needed to fill a tank.

Before solving it, the model can generate an example of a similar rate problem, such as calculating how long a machine takes to produce a certain number of items.

It can then use the shared mathematical structure to solve the new problem.

The advantage is that the examples are generated by the model instead of being manually labelled in advance. They can also be tailored to the individual problem.

The lecture reports that analogical prompting outperformed zero-shot CoT and manual few-shot CoT in the experiments discussed.

### Generating useful background knowledge

Analogical prompting can also include generating high-level knowledge before solving a problem.

For a coding task, the model might:

1. Identify the algorithms relevant to the task.
2. Explain the main algorithmic ideas.
3. Generate illustrative examples.
4. Return to the original problem and apply that knowledge.

This gives the model both relevant examples and a broader understanding of the problem-solving approach.

## 8. Automatic prompt engineering

Different instructions can produce different results from the same LLM.

For example, one prompt might ask for a direct answer, while another asks the model to decompose the problem and verify intermediate results.

Finding the best instruction manually can require substantial trial and error.

**Automatic prompt engineering** uses an LLM to propose prompts and evaluates their performance.

A basic workflow is:

1. Describe the task.
2. Ask an LLM to generate candidate instructions.
3. Evaluate the instructions on a validation set.
4. Measure how accurately each instruction performs.
5. Select promising instructions.

The lecture describes evaluating candidate instructions on a relatively small validation set, around 100 problems in the example discussed.

### LLMs as optimizers

A more iterative approach treats one LLM as the optimizer and another component or model as the evaluator.

- **Optimizer:** Proposes a new instruction based on previous attempts.
- **Evaluator:** Measures the accuracy or performance of that instruction.

The optimizer can use a history of candidate solutions and their scores to guide further proposals. If the history becomes too large for the context window, older entries may be removed.

This approach is known as Optimization by PROmpting (OPRO) in the associated research.

The key idea is to improve prompts using measured results rather than relying entirely on human intuition.

## 9. Other prompting strategies for reasoning

The lecture also discusses techniques that guide the structure of the model's reasoning.

### Least-to-most prompting

The model decomposes a difficult problem into smaller subproblems, solving easier parts before harder ones.

For example, a complex mathematical problem might require calculating two intermediate values before the final result can be obtained.

The model solves the smaller components and uses their results to solve the original problem.

### Dynamic least-to-most prompting

This extends the basic idea by dynamically selecting relevant examples for individual subproblems.

Instead of using exactly the same examples throughout the task, the model can use examples better suited to the current subproblem.

### Self-Discover

Self-Discover asks the model to compose a reasoning structure suited to the task.

Rather than manually providing a specific reasoning procedure for every problem, the model selects and organizes a suitable structure before solving it.

**Main lesson from Part 1:** We can improve a single generation by guiding the model's reasoning, providing relevant examples, generating useful background knowledge, and optimizing the instructions.

# Part 2: Search and Selection — Increasing Width

Generating a single solution explores only one possible path. What if the model makes a mistake early in that path?

The second approach increases the width of exploration by generating multiple candidates and selecting a promising answer.

## 10. Why generate multiple solutions?

Suppose a model generates three solutions to a mathematics problem:

- Candidate A: 42
- Candidate B: 48
- Candidate C: 48

If the two candidates that independently produce 48 are correct, selecting 48 may be better than accepting the first candidate.

However, the model still needs a method to choose among the candidates.

Ideally, we would have a reliable evaluator that knows which answer is correct. In many real-world tasks, such an evaluator is unavailable.

The lecture discusses several ways to handle this challenge.

## 11. Self-consistency

**Self-consistency** generates multiple reasoning paths and selects the final answer that appears most consistently across them.

The workflow is:

1. Prompt the model to solve the problem using reasoning.
2. Generate multiple diverse responses.
3. Extract the final answer from each response.
4. Count how often each answer appears.
5. Select the most frequent answer.

The reasoning paths do not need to be identical. Different paths can reach the same final answer.

### Example

Suppose five independent attempts produce:

| Attempt | Final answer |
|---|---:|
| 1 | 24 |
| 2 | 24 |
| 3 | 18 |
| 4 | 24 |
| 5 | 18 |

The answer 24 receives three votes, while 18 receives two. Self-consistency selects 24.

This does not mathematically prove that 24 is correct. It is a selection strategy that can improve accuracy when correct answers are sufficiently consistent across diverse samples.

### Why not choose the highest-probability response?

A basic alternative is to generate multiple responses and choose the one with the highest model probability or log probability.

The lecture notes that self-consistency can perform substantially better than this sample-and-rank baseline, unless the model has been trained to be a good verifier.

The reason is that a model's confidence in generating a response does not necessarily correspond to the response being correct.

### How do we obtain diverse responses?

If every attempt follows nearly the same path, multiple generations may repeat the same mistake.

Sampling methods such as temperature adjustment and nucleus sampling can encourage diversity.

The goal is to explore different plausible reasoning paths rather than repeatedly generating almost identical answers.

## 12. Beam search and prompt ensembles

The lecture also discusses other ways of generating or exploring alternatives.

### Beam search

Beam search keeps the top \(k\) partial sequences according to their probabilities during decoding.

Instead of maintaining only one continuation, it maintains several promising continuations and expands them as generation proceeds.

Beam search is a decoding strategy; it is not the same as self-consistency, which compares final answers from multiple sampled reasoning paths.

### Prompt ensembles

An ensemble can apply greedy decoding to multiple prompt variants of the same problem.

Each prompt variant may elicit a different answer. The resulting outputs can then be compared or combined.

The general principle is to reduce dependence on one particular prompt or generation path.

## 13. Candidate selection for code generation: AlphaCode

Selecting the correct answer is especially challenging in competitive programming.

A programming problem may contain:
- A long natural-language description.
- A small set of sample input-output pairs.
- Hidden test cases that the submitted program must also pass.

A program that passes the visible examples may still be incorrect.

The lecture discusses the candidate-selection approach used in AlphaCode.

### Execution-based clustering

Instead of relying only on a language model to judge code, candidate programs can be executed on generated test inputs.

The process is:

1. Train or use a model to generate additional test inputs for the problem.
2. Execute the candidate programs on these inputs.
3. Group programs that produce the same outputs.
4. Treat programs in the same cluster as potentially semantically equivalent, provided the generated inputs are sufficiently diverse and informative.
5. Select representative programs from the largest clusters.

In the approach described in the lecture, one program is sampled from each of the ten largest clusters.

The key idea is that programs with similar behavior across many test inputs may be solving the same problem in equivalent ways.

However, matching outputs on a finite set of tests does not prove that two programs are equivalent on every possible input.

### What were the results?

The lecture notes that clustering provides an additional performance improvement over filtering candidates alone.

However, the resulting performance still falls short of an oracle selector—an idealized selector that can always identify the correct solution.

## 14. Universal self-consistency

Ordinary self-consistency works well when final answers can be extracted and compared, such as numerical answers.

But what if the outputs are open-ended?

For example:
- Summaries.
- Explanations.
- Long-form question answering.
- Natural-language responses with different wording.

Two correct answers may express the same meaning using different sentences, so exact-match voting is not appropriate.

**Universal self-consistency** asks an LLM to compare the generated responses and select the one that is most consistent with the majority.

The process is:

1. Generate multiple responses.
2. Present the candidate responses to an LLM.
3. Ask it to identify the answer that best represents the common consensus.
4. Return the selected response.

The lecture reports that this approach improves over a baseline on open-ended generation tasks. It can also match ordinary self-consistency performance on mathematics and coding tasks without requiring explicit answer extraction or code execution.

Its performance is limited by the model's ability to process and compare all the candidate responses in its context window.

The intuition is that judging which answer best agrees with other answers may be easier than independently determining which answer is objectively correct.

## 15. LLM-based verifiers and reward models

Consistency is useful, but multiple models can agree on the same wrong answer.

A stronger approach is to train or use a verifier that evaluates candidate solutions.

A **verifier** is a model or system that estimates whether a solution is correct or how good it is.

The lecture distinguishes two important types of reward models.

### Outcome-supervised Reward Model (ORM)

An ORM evaluates the completed solution.

It asks, in effect:

> Is the final answer correct or good?

For example, it might score a complete mathematical solution after all calculations have been performed.

### Process-supervised Reward Model (PRM)

A PRM evaluates individual reasoning steps.

Instead of only judging the final answer, it estimates whether intermediate steps are correct or promising.

For example, it can evaluate each calculation in a mathematical solution.

### Why evaluate individual steps?

Imagine two solutions that end with the same answer, but one contains a flawed intermediate step.

A final-answer evaluator may fail to reveal where the reasoning went wrong. A process evaluator can identify problems earlier in the sequence.

The lecture reports that strong LLM-based verifiers can outperform consistency-based selection. It also notes that PRMs scale better with additional samples than ORMs and majority-voting baselines in the experiments discussed.

These results depend on verifier quality and the task being evaluated.

## 16. Tree of Thoughts and search

So far, many selection methods generate complete responses first and evaluate them afterward.

However, if we can evaluate partial reasoning steps, we can search through the solution space before completing a response.

This motivates **Tree of Thoughts (ToT)**.

Instead of following one reasoning path, the model explores a tree of possible intermediate thoughts.

Each node represents a possible state or partial solution. Different branches represent alternative next steps.

The workflow is:

1. Generate possible next reasoning steps.
2. Evaluate how promising each step is.
3. Expand promising branches.
4. Stop exploring unpromising branches.
5. Continue until a solution is found or the search budget is exhausted.

### Example: The Game of 24

Suppose the numbers are 4, 6, 7, and 8. The task is to use arithmetic operations to obtain 24.

At each step, the model proposes operations involving two numbers.

A state evaluator estimates whether the remaining numbers and current result can still lead to 24.

The system prioritizes promising operations instead of blindly following the first one.

The lecture describes basic breadth-first search (BFS) and depth-first search (DFS) as possible search algorithms. More advanced methods, such as Monte Carlo Tree Search (MCTS), can also be integrated.

### Why is tree search useful?

It combines generation with evaluation at intermediate stages.

This allows the system to spend more computation on promising directions and less on paths that are unlikely to succeed.

**Main lesson from Part 2:** Generating alternatives is only half the problem. The system also needs a reliable way to compare, rank, verify, or search through those alternatives.

# Part 3: Iterative Self-Improvement — Increasing Depth Through Feedback

The third approach generates a solution, receives feedback, and revises the solution repeatedly.

This is different from generating multiple independent candidates and choosing one.

## 17. Why iterative improvement is needed

Even strong LLMs make mistakes.

Generating multiple solutions can reduce dependence on a single attempt, but it does not automatically repair the mistakes in an individual solution.

Iterative self-improvement adds a feedback loop.

The basic process is:

1. Generate an initial solution.
2. Evaluate or critique it.
3. Identify possible problems.
4. Revise the solution.
5. Repeat until a stopping condition is reached.

This resembles how people solve difficult problems: they produce an initial attempt, examine what went wrong, and make corrections.

However, an LLM's ability to improve depends heavily on the quality of the feedback it receives.

## 18. Reflexion

**Reflexion** uses natural-language feedback to help an agent learn from previous attempts.

The system records a reflection on what went wrong and uses it as additional context in a subsequent attempt.

A simplified workflow is:

1. The agent attempts a task.
2. The environment or evaluator provides feedback.
3. The agent produces a textual reflection about the failure or mistake.
4. The reflection is retained as context.
5. The agent tries again using the lesson from the previous attempt.

The lecture notes that Reflexion can improve performance on tasks with effective evaluation heuristics, such as ALFWorld.

The important idea is that an agent can use a textual record of earlier failures to guide future behavior without necessarily updating its model weights.

## 19. Self-Refine

**Self-Refine** uses a generate-feedback-refine loop to improve an output.

The model generates a solution, provides feedback on that solution, and then generates a revised version.

When available, external evaluation can be combined with the model's own feedback.

The general process is:

- Generate an initial answer.
- Critique the answer.
- Revise the answer using the critique.
- Repeat as needed.

Reflexion and Self-Refine are related, but their emphasis differs. Reflexion highlights learning from previous attempts through retained textual reflections, while Self-Refine emphasizes iterative refinement of an output through feedback.

Neither approach guarantees improvement if the feedback is misleading.

## 20. Self-Debugging

Code generation provides a natural setting for iterative improvement because programs can often be executed and tested.

**Self-Debugging** uses code inspection, explanation, and available execution feedback to help a model identify and fix programming errors.

The lecture lists four useful feedback formats.

### A. Simple feedback

Provide a short, general indication that the generated code is wrong.

Example:

> The solution is incorrect. Try again.

This is easy to provide but does not reveal the specific cause of the failure.

### B. Unit-test feedback

Provide the model with the results of executing tests.

For example, a test may expect a function to return 10 but report that the actual result is 8.

This gives the model concrete evidence about the program's behavior.

### C. Code explanation

Ask the model to explain the implementation line by line.

Explaining the code can help reveal incorrect assumptions, conditions, or calculations.

### D. Execution trace

Provide a step-by-step record of what happened during execution, including relevant intermediate values or operations.

This can help identify where the program diverges from the expected behavior.

The lecture reports that Self-Debugging consistently improves performance across different LLMs, and that more informative feedback can improve debugging further.

The important distinction is that explanations and execution results are not equally reliable: an explanation can be mistaken, while actual test results provide evidence of observed program behavior.

## 21. Can an LLM correct its own reasoning without external feedback?

This is one of the lecture's most important warnings.

Some earlier approaches report improvements from self-correction when the model receives a reliable verifier or the correct answer.

But in many real-world tasks, such an oracle is unavailable.

Without external feedback, the model must judge whether its own answer is correct.

The lecture discusses research finding that **self-correction without oracle feedback can reduce reasoning performance**.

Why?

1. The model generates an answer.
2. It tries to determine whether that answer is correct.
3. It may misjudge the answer.
4. It revises a correct answer or retains an incorrect one.
5. The final result becomes worse.

Changing the wording of a general feedback prompt can change the model's behavior, including its tendency to retain its original answer. However, the lecture notes that the prompt variants discussed did not significantly improve performance over the initial results.

The key lesson is that asking a model to reconsider its answer does not guarantee that it can identify its own mistakes.

## 22. What about multi-agent debate?

Multi-agent debate uses several model responses or agents to examine a problem.

A simplified process is:

1. Generate several responses in parallel.
2. Ask the model or agents to review the different responses.
3. Produce an updated answer.

This sounds powerful because different responses may reveal different perspectives.

However, the lecture notes that multi-agent debate did not outperform self-consistency in the comparison discussed.

When the same number of responses and a similar token budget are available, self-consistency can use the computation more effectively than debate without a strong evaluator.

The broader lesson is that adding more agents or more discussion does not automatically improve accuracy. The system needs a useful way to evaluate the alternatives.

# 23. Combining Techniques: How Should We Spend the Inference Budget?

The three approaches can be combined, but the best combination depends on the model, task, and available computation.

For example, a system could:

1. Use CoT prompting to generate a structured solution.
2. Generate several candidate solutions.
3. Use self-consistency or a verifier to select promising candidates.
4. Use feedback to revise a candidate.
5. Verify the final result.

However, every additional generation, evaluation, and revision consumes computation.

The goal is not to spend the maximum possible amount of computation. It is to spend the available budget where it produces the greatest improvement.

## 24. Parallel generation versus sequential refinement

There are two broad ways to spend additional computation.

### Parallel generation

Generate multiple candidates independently.

**Advantages:**
- Explores different solution paths.
- Reduces dependence on one initial attempt.
- Can work well when different candidates make different mistakes.

**Limitations:**
- Requires a method to select the best candidate.
- Multiple candidates may repeat the same error.
- Consumes additional inference resources.

### Sequential refinement

Generate one solution, critique it, and revise it through repeated steps.

**Advantages:**
- Allows feedback to guide subsequent attempts.
- Can focus effort on a known weakness.
- Is useful when errors can be detected and explained.

**Limitations:**
- Depends on the quality of the feedback.
- A mistaken critique can make a solution worse.
- Repeated calls increase latency and cost.

### Which is better?

The lecture presents this as an empirical question: the best choice depends on the model's capabilities and the task.

Its discussion of research on inference-time compute scaling suggests that:

- For simpler problems, self-correction may be more useful because the model can often recognize and repair its mistakes.
- For harder problems, a balance involving parallel generation may work better than relying entirely on sequential self-correction.

These are general findings from the research discussed, not a universal rule for every model or problem.

## 25. Model size and inference cost

Model size also affects how computation should be allocated.

Under the same floating-point operations (FLOPs) budget, a smaller model may be able to generate more candidate solutions than a larger model.

A larger model may perform better on an individual attempt, while a smaller model may allow more attempts within the same budget.

Therefore, the best model can depend on how much inference-time computation is available.

The right question is not simply:

> Which model is the largest?

It is also:

> Which model and inference strategy produce the best result within my budget?

This requires empirical evaluation of model quality, number of samples, verifier quality, and total cost.

# 26. Practical Example: Designing a Reasoning Agent

Imagine building an AI agent that solves programming problems.

A practical design could combine several techniques from the lecture.

### Step 1: Understand the task

The agent reads the problem and identifies the required inputs, outputs, and constraints.

### Step 2: Generate a structured solution

Use suitable prompting to encourage decomposition and planning.

### Step 3: Generate alternatives

If the problem is difficult, produce several candidate approaches or programs.

### Step 4: Evaluate the candidates

Use available tests, execution results, or a trained verifier to identify promising candidates.

### Step 5: Debug failures

Provide failing test cases or execution traces to the model so it can identify and repair errors.

### Step 6: Verify the final solution

Run the final program against the available tests and other relevant checks.

### Step 7: Stop when appropriate

Stop when the solution satisfies the required checks, the quality target is reached, or the inference budget is exhausted.

This design combines depth, width, and iterative feedback rather than relying on a single prompt or a single model response.

# 27. Final Takeaways

The lecture presents three major ways to improve LLM reasoning at inference time.

**1. Depth — Improve one generation**

Use Chain-of-Thought, zero-shot CoT, analogical prompting, prompt optimization, and structured reasoning strategies to guide the model through a problem.

**2. Width — Explore multiple candidates**

Use self-consistency, ensembles, candidate clustering, verifiers, and tree search to explore alternative solutions and select promising ones.

**3. Iteration — Improve through feedback**

Use Reflexion, Self-Refine, and Self-Debugging to revise outputs using critiques, test results, or other available evidence.

The lecture also emphasizes three important cautions:

- More computation does not automatically mean better answers.
- Self-correction without reliable feedback can make reasoning worse.
- The best combination of model size, candidate generation, evaluation, and refinement depends on the task and the available budget.
